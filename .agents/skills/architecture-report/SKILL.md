# Architecture Report

Скилл для составления архитектурных отчётов (планы, анализ, гипотезы).

## Когда использовать

Загружай этот скилл, когда пользователь:

- просит создать отчёт о проектировании / декомпозиции / миграции
- просит описать архитектуру системы
- просит разобрать проблему и предложить метод решения
- говорит «сделай отчёт как тот, в reports/...», «напиши план»
- просит отчёт про контейнеризацию, микросервисы, интеграцию симуляторов

НЕ используй для отчётов о результатах тестов (там нужны данные/цифры),
но общие принципы стиля применимы и там.

## Главный принцип: без кода

**В отчёте НЕ должно быть фрагментов кода.** Запрещено приводить:

- Dockerfile / compose.yml / Makefile целиком или фрагментами
- команды bash (apt-get install, colcon build, docker ...)
- блоки YAML/XML/JSON конфигурации
- код на Python/Rust/C++
- имена переменных, функций, сигнатуры

Разрешено:
- таблицы (компоненты, сервисы, риски)
- mermaid-диаграммы (архитектура, графы)
- описательные списки
- короткие упоминания имён файлов/сервисов/пакетов (без содержимого)

Исключение: если пользователь явно просит показать код — тогда можно.
По умолчанию — не показывать.

## Структура отчёта

Отчёт пишется на русском, в Markdown, с оглавлением.

**Требование к объёму: отчёт должен быть не менее 1000 строк.**
Это гарантирует глубину проработки: каждый раздел раскрывается полно,
гипотезы — с обоснованием, методы — с деталями, риски — с митигациями.
Короткий отчёт (< 1000 строк) считается неполным — его нужно углубить
(добавить подразделы, примеры сценариев, сравнительные таблицы, больше
диаграмм, обоснования решений и альтернатив), а не искусственно растянуть.

Рекомендуемые разделы (порядок и состав подстраиваются под тему):

### 1. Резюме (Executive Summary)

- Зачем это нужно, что предлагается (3-5 предложений)
- Ключевые решения в виде таблицы
- Главная идея одной фразой

### 2. Текущее состояние: что есть сейчас

- Факты, проверенные в системе (кто где работает, какие компоненты)
- Таблица «компонент / где работает / комментарий»
- Обязательно проверять фактическое состояние, а не предполагать
  (например: `docker ps`, процессы, структура — но результаты подавать
  описательно, не командами)

### 3. Гипотеза проблемы

- Сформулировать, в чём именно проблема (не симптом)
- Развернуть гипотезу в явные утверждения «если ... то ...»
- Опираться на факты из раздела 2

### 4. Почему прошлый план устарел (если применимо)

- Сравнить старое и новое состояние по ключевым осям
- Таблица «было / стало»
- Явно указать, что именно перестало быть верным

### 5. Целевая архитектура

- Mermaid-диаграмма (graph TB/LR)
- Принцип работы одной фразой
- Что является заменяемым элементом

### 6. Сервисы / компоненты и их ответственность

- Для каждого: что делает, что не содержит, как проверяется готовность
- Что намеренно исключено и почему

### 7. Метод решения

- Подход словами (без команд)
- Карта «компонент → что ему нужно» (таблица)
- Mermaid-диаграммы для слоёв/потоков при необходимости

### 8. Коммуникация / интеграция

- Как компоненты общаются (словами)
- Синхронизация времени/данных
- Mermaid-диаграмма взаимодействия

### 9. Порядок внедрения

- Таблица «этап / действие / критерий готовности»
- Этапы логически зависимы, каждый имеет проверяемый результат

### 10. Ожидаемый эффект

- Таблица «сценарий / было / станет»
- Числа по возможности (время, ресурсы)

### 11. Риски и митигации

- Таблица «риск / вероятность / влияние / митигация»
- Отдельно ограничения (чего нельзя сделать)

### 12. Связанные отчёты

- Список ссылок на предыдущие отчёты в reports/ с одной строкой описания

## Правила подачи

- **Язык**: русский, деловой стиль, без воды
- **Оглавление**: в начале, с якорями на разделы
- **Иллюстрации**: mermaid-диаграммы (см. `.agents/skills/mermaid-diagrams/SKILL.md`)
- **Таблицы**: для сравнений, сервисов, рисков
- **Факты**: проверять в системе (docker ps, процессы, файлы) — не выдумывать
- **Не показывать код**: см. «Главный принцип»
- **Дата и ветка**: в шапке отчёта (дата — текущая, ветка — `git branch --show-current`)
- **Путь**: `reports/<подпапка>/<дата>_<тема>.md` (подпапка — по тематике)

## Проверка перед сдачей

Перед завершением проверь:

1. Нет ли в отчёте фрагментов кода? (`grep -cE "FROM |RUN |CMD |colcon build|apt-get install|docker exec" файл` должно давать 0)
2. Есть ли оглавление?
3. Есть ли хотя бы одна mermaid-диаграмма?
4. Гипотеза проблемы сформулирована явно?
5. Факты проверены, а не выдуманы?
6. Указаны дата и ветка?
7. Объём ≥ 1000 строк? (`wc -l файл` должно быть ≥ 1000; если меньше — углубить отчёт)
