# Commit Review

Скилл для подготовки коммита: ревью кода + составление отчёта.

## Когда использовать

Загружай этот скилл, когда пользователь:

- просит проверить код перед коммитом
- просит составить отчёт о проделанной работе
- говорит «подготовь к коммиту», «сделай ревью», «напиши отчёт»

## Процесс работы

### Шаг 1: Посмотреть изменения

Выполни `git diff --cached` чтобы увидеть уже проиндексированные файлы.
Если изменений нет — выполни `git --no-pager diff` чтобы увидеть
непроиндексированные изменения. Также посмотри `git --no-pager status`.

### Шаг 2: Понять контекст

Посмотри, какие файлы изменены. Если нужно — прочитай ключевые изменения
в файлах, чтобы понять суть работы.

### Шаг 3: Ревью кода (codereview)

Проанализируй изменения по следующим критериям:

#### Для Python кода

- **Логирование**: нет ли `print()` в production коде? Должен быть `_log.info/warning/error`
- **Производительность**: нет ли `for i in range()` над большими массивами (>10К итераций)?
  Если есть — нужен `@njit` или numpy векторизация
- **Импорты**: нет ли import внутри функций/методов? Должны быть наверху модуля
- **Numba**: `@njit` без `cache=True` (read-only fs в контейнере)
- **Numpy**: использовать векторизацию вместо циклов где возможно
- **Типизация**: добавлены ли type hints для новых функций?
- **Ошибки**: нет ли `except: pass` без логирования?

#### Для Docker / сборки

- **Layer cache**: нет ли `--no-cache` в production сборках? (`make build-no-cache` — допустим)
- **Syntax**: нет ли `# syntax=docker/dockerfile:1.4`? Должен быть удалён

#### Для коммита

- **Формат**: соответствует ли сообщение `type(scope): описание`?
- **Длина**: заголовок до 50 символов, тело до 72?
- **Язык**: русский, повелительное наклонение, без точки в конце?
- **Тип**: `feat/fix/docs/style/refactor/test/chore`?

Если находишь проблемы — сообщи о них пользователю и предложи исправить.
Не исправляй самостоятельно без согласия пользователя.

### Шаг 4: Составить отчёт

Создай файл `reports/<дата_время>.md`, где `<дата_время>` — текущая
дата и время в формате `YYYY-MM-DD_HHMMSS` (например, `2026-06-01_011400`).

**Правила определения времени:**

- Используй системное время (`date +%Y-%m-%d_%H%M%S`) — оно уже в локальной таймзоне.
- Не конвертируй UTC ↔ MSK и не добавляй/вычитай часовые пояса.
- Заголовок отчёта должен содержать то же время, что и имя файла,
  с указанием таймзоны системы (`date +%Z`).

Шаблон отчёта (также в `reports/template.md`):

```markdown
# Report <дата и время> <таймзона>

**Branch:** <ветка>
**Stats:** <статистика изменений>

## Что было добавлено

- Перечисли новые файлы, новые функции, новые фичи

## Что было изменено

- Перечисли изменения в существующем коде

## Проблемы

- Какие проблемы/ошибки встретились в процессе

## Как были решены

- Как эти проблемы были решены

## Что нужно учитывать в будущем

- Что стоит помнить при дальнейшей работе
```

Заполни каждый раздел на основе анализа изменений.
Если информации недостаточно — задай пользователю уточняющие вопросы.

### Шаг 5: Выполнить коммит по правилам

Перед коммитом:

1. **Проверить формат** по правилам из `.agents/skills/commit-format/SKILL.md`
2. **Проверить стиль** по правилам из `.agents/skills/python-code-style/SKILL.md`
3. **Проверить Docker** по правилам из `.agents/skills/docker-build-rules/SKILL.md`
4. **Дождаться команды** пользователя — не коммитить без явного запроса

## Важные замечания

- Не выполнять commit и push без явной команды пользователя
- Отчёт добавляется в `git add`, но коммитится вместе с кодом
- Если pre-commit hook генерирует пустой отчёт — перезаписать его содержимым
- Не менять файлы вне области задачи пользователя
