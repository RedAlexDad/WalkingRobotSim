# Troubleshooting Report

Скилл для отчётов об ошибках, проблемах, гипотезах и решениях.

## Когда использовать

Загружай этот скилл, когда пользователь:

- просит отчёт о развёртывании (deployment) системы/сервиса
- просит отчёт об эксплуатационных проблемах (operation issues)
- просит описать найденные и решённые ошибки/баги
- говорит «оформи как в NIIAS/drs_server», «как 02-deployment-report»,
  «как 04-operation-issues»
- просит задокументировать ход отладки с гипотезами

Этот скилл отличается от `architecture-report`: здесь фокус — на
**проблемах и их решении** (цепочка симптом→причина→решение),
а не на архитектуре/планах. Оба скилла можно комбинировать.

Отчёт строится по единому формату: Часть A (развёртывание) + Часть B
(эксплуатационные проблемы) в одном файле. Пример —
`reports/isaam/2026-08-22_simulation-issues-report.md`.

---

## Структура отчёта

Отчёт на русском, Markdown, с оглавлением и шапкой:

```markdown
# <Название отчёта>

**Дата:** YYYY-MM-DD
**Ветка:** `имя-ветки`
**Версия:** 1.0

---

## Содержание
...
```

## Единый формат отчёта

Отчёт состоит из **двух взаимосвязанных частей в одном файле**:

- **Часть A: Развёртывание (Deployment Report)** — как система разворачивалась
- **Часть B: Эксплуатационные проблемы (Operation Issues)** — детальное описание проблем

### Взаимосвязь частей A и B

Части связаны по принципу «**развёртывание сталкивается с проблемами → детали — в Части B**»:

- Часть A — это **связное повествование** о развёртывании: что делалось, какие решения приняты, что было развёрнуто в итоге.
- Когда в ходе работ (п. «Ход работ») развёртывание **сталкивается с проблемой**, Часть A не разворачивает её детально, а **кратко описывает и ссылается** на соответствующий раздел Части B: «см. Проблема N».
- Часть B — это **справочник по проблемам**: каждая проблема детально разобрана по цепочке «Симптом → Гипотезы → Причина → Диагностика → Решение → Результат».
- Сводная таблица проблем в Части A (A.4) и в Части B — по сути один и тот же перечень; в Части A она краткая (что/причина/решение/статус), в Части B — с гипотезами, методами и сложностью.

Читатель идёт так: Часть A даёт контекст развёртывания, встречает «Проблема 9» → переходит к Проблеме 9 в Части B → возвращается и продолжает чтение Части A.

```mermaid
graph LR
    A["Часть A: Развёртывание<br/>ход работ, архитектура"]
    B["Часть B: Проблемы<br/>детальные разборы"]
    A -->|"столкнулись с проблемой —<br/>'см. Проблема 9'"| B
    B -->|"решение найдено —<br/>продолжение развёртывания"| A
```

### Часть A: Развёртывание

1. **Введение** — предпосылки, цели, оборудование (таблица)
2. **Выбор решения (история)** — сравнение вариантов таблицей,
   почему выбран/отвергнут каждый; хронология решений
3. **Ход работ** — пошагово с подразделами: действие → ошибка →
   причина → решение → результат. Провалы и успехи фиксируются честно.
   **Встретив проблему — кратко описать её и сослаться на Часть B:**
   «Причина: дублирующий блок ros2_control (подробно — Проблема 8 в Части B)»
4. **Проблемы и решения** — сводная таблица (что/причина/решение/статус)
   со ссылками на детальные разделы Части B (нумерация проблем сквозная)
5. **Итоговая архитектура** — схема, таблица компонентов, параметры,
   сравнение «было / стало»
6. **Дальнейшие шаги** — кратко- / средне- / долгосрочные (чек-листы)
7. **Приложения** — A: команды администрирования; B: полезные файлы;
   C: отдельные сложные проблемы с решениями

### Часть B: Эксплуатационные проблемы

1. **Сводная таблица** (в начале!) — колонки:
   `№ | Проблема | Гипотезы | Причина | Решение | Методы | Сложность`
2. Каждая проблема — отдельным разделом (см. блок «Проблема»), детально
   по цепочке Симптом → Гипотезы → Причина → Диагностика → Решение → Результат
3. **Итоговая статистика** — таблица: всего проблем, решено,
   сложность (🟢/🟡/🔴), результаты проверок

**Нумерация:** сквозная. Разделы A.1–A.7 в Части A, затем проблемы в
Части B продолжают нумерацию (проблемы 8, 9, 10...). Это позволяет
ссылкам «Проблема N» из Части A вести на раздел в Части B.

### Гиперссылки (обязательно)

Все перекрёстные ссылки между частями — **рабочие гиперссылки** (якоря
Markdown), а не просто текст «см. Проблема N». Клик должен вести на
целевой раздел.

**Правила:**

1. **Только реальные гиперссылки:** `[Проблема 8](#8-проблема-...)`
   и `[см. A.3.3](#a33-запуск-симуляции)`. Не писать голый текст
   «см. Проблема N» без ссылки.
2. **Анкер соответствует заголовку.** GitHub-якорь строится из текста
   заголовка: строчные буквы, пробелы → дефисы, убираются точки/запятые,
   спецсимволы. Например:
   - заголовок `## 8. Проблема: Сломанный контроллер` →
     якорь `#8-проблема-сломанный-контроллер`
   - заголовок `#### A.3.3. Запуск симуляции` →
     якорь `#a33-запуск-симуляции` (точки в номере убираются)
3. **Проверять каждый якорь перед сдачей:** убедиться, что целевой
   заголовок существует с точным текстом, из которого строится якорь.
4. **Двусторонняя связь:** из Части A — ссылка на раздел Части B,
   из Части B — обратная ссылка на этап Части A (см. блок «Связь с
   развёртыванием»). Обе — гиперссылки.

**Проверка перед сдачей (см. чек-лист):** пройтись по всем ссылкам —
у каждого `[текст](#якорь)` найти соответствующий заголовок `# ...`
в файле. Ссылка без целевого заголовка считается ошибкой.

## Блок «Проблема» (ядро формата)

Каждая проблема оформляется по единой цепочке:

```
### N. Проблема: <короткое имя>

### N.1. Симптом
Что видит пользователь/система. Реальные сообщения об ошибках,
лог-строки, статусы. Без догадок — только факты.

### N.2. Гипотезы
Первые предположения о причине (что казалось виновным сначала).
Для **каждой** гипотезы явно указать вердикт: **✅ принята** (подтвердилась
как причина) или **❌ опровергнута** (не подтвердилась — и почему отпала).
Пример:

- ❌ Гипотеза A: сломан плагин ros2_control — опровергнута (класс
  корректен, до фикса он даже не загружался)
- ✅ Гипотеза B: конфликт интерфейсов из-за дублирования joint —
  принята (подтвердилась как причина в [N.3](#n3-причина))

Опровергнутые гипотезы важны — они показывают, что диагностика
шла не вслепую, а исключала варианты.

**Ссылки на N.3:** фраза «подтвердилась как причина в N.3» — это
**гиперссылка** на раздел [N.3. Причина](#n3-причина), а не голый текст.

### N.3. Причина
Истинная первопричина после диагностики. Конкретно: какой компонент,
какой параметр, какая конфигурация. Связь «симптом ↔ причина» явная.

### N.4. Диагностика
Какие команды/проверки выполнялись, что они показали.
Цепочка от наблюдения к причине. Реальные выводы команд.

### N.5. Решение
Что сделано для исправления. Пошагово.

### N.6. Исправление в скриптах/конфигах (если применимо)
Что изменено в скриптах/манифестах, чтобы решение применялось
автоматически при повторном деплое (не только руками).

### N.7. Результат
До / После (таблица или выводы). Метрика, которая подтверждает,
что проблема решена.
```

## Правила подачи

- **Язык:** русский, деловой стиль
- **Сводная таблица проблем** — обязательна (в Части B). Колонки:
  `№ | Проблема | Гипотезы | Причина | Решение | Методы | Сложность`
  Плюс краткая сводная таблица проблем в Части A (A.4).
- **Сложность:** 🟢 (<1ч), 🟡 (1-4ч), 🔴 (>4ч)
- **Статус:** `[x]` решено, `[ ]` не решено
- **Команды диагностики:** допускаются, но короткие и по делу
  (проверка, вывод). Не копировать большие листинги конфигов целиком —
  достаточно фрагментов с пояснением
- **Факты:** реальные сообщения об ошибках и выводы команд — да;
  догадки — только в разделе «Гипотезы», каждая с вердиктом
  **✅ принята / ❌ опровергнута** (см. блок «Проблема», N.2)
- **Хронология:** фиксировать провальные попытки честно (что пробовали,
  почему не сработало) — это ценность отчёта
- **Таблицы** для: сравнения вариантов, компонентов, «было/стало»,
  статистики
- **Диаграммы:** mermaid (см. `.agents/skills/mermaid-diagrams/SKILL.md`)
  для архитектуры/потоков, если применимо
- **Дата и ветка:** в шапке; ветка — `git branch --show-current`
- **Путь:** `reports/<подпапка>/<дата>_<тема>.md`
- **Валидация:** перед сдачей обязательно запустить
  `python3 scripts/check_report.py <отчёт.md>` — он ловит галлюцинации
  ИИ в нумерации, ссылках и структуре (см. раздел «Валидатор отчёта»)

## Итоговая статистика (конец отчёта)

Для Части B — обязательна:

| Метрика | Значение |
|---------|----------|
| Всего проблем | N |
| Из них решено | N |
| 🟢 (<1ч) | N |
| 🟡 (1-4ч) | N |
| 🔴 (>4ч) | N |
| Ключевые выводы | ... |

## Валидатор отчёта (защита от галлюцинаций)

Отчёты пишет ИИ, поэтому нумерация и ссылки могут содержать
галлюцинации (пропущенный номер, битая ссылка, отсутствующий подраздел).
**Перед сдачей запускать автоматический валидатор:**

```bash
python3 scripts/check_report.py reports/<...>/<отчёт>.md
```

Валидатор проверяет:

1. **Ссылки** — каждая `[..](#якорь)` ведёт на существующий заголовок
   или HTML-якорь (`<a id="...">`); учитывает дубли заголовков (суффиксы -1, -2)
2. **Нумерация проблем** — сквозная, без пропусков и дублей
3. **Подразделы** — у каждой проблемы есть N.1..N.7
   (Симптом, Гипотезы, Причина, Диагностика, Решение,
    Исправление, Результат)
4. **Вердикты гипотез** — каждая гипотеза помечена ✅ или ❌
5. **Связь с Частью A** — у каждой проблемы есть блок
   «Связь с развёртыванием (Часть A)»

Валидатор возвращает 0 при успехе, 1 при ошибках. Все ошибки должны
быть исправлены до сдачи отчёта.

## Проверка перед сдачей

0. **Запущен ли валидатор?** `python3 scripts/check_report.py <отчёт.md>`
   → должен вернуть 0 (все проверки пройдены)
1. Есть ли оглавление и шапка (дата/ветка/версия)?
2. Часть A по 7 пунктам: Введение, Выбор решения (история), Ход работ, Проблемы и решения, Итоговая архитектура, Дальнейшие шаги, Приложения?
3. Часть B: каждая проблема по цепочке Симптом → Гипотезы → Причина → Диагностика → Решение → Результат?
4. Есть ли сводная таблица проблем в Части B (№ | Проблема | Гипотезы | Причина | Решение | Методы | Сложность)?
5. Реальные симптомы/ошибки записаны, а гипотезы — с вердиктами ✅ принята / ❌ опровергнута?
6. Провальные попытки зафиксированы, а не скрыты?
7. Есть ли «было / стало» и метрика подтверждения решения?
8. Есть ли итоговая статистика (Часть B)?
9. Нумерация сквозная (A.1–A.7 → проблемы 8, 9, ...)?
10. Части связаны: проблемы в Части A ссылаются на детальные разделы Части B?
11. **Все перекрёстные ссылки — рабочие гиперссылки?** Для каждой
    `[текст](#якорь)` существует целевой заголовок (текст совпадает с
    тем, из которого строится якорь). Голых текстов «см. Проблема N»
    без ссылки нет.
12. Ветка и дата верны?
