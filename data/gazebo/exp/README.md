# Пилотная проверка YOLO в Gazebo

Проверка выбора модели МО для статьи ИИАСУ-2026: выполняется ли ограничение
`T ≤ 0.1 с` на CPU и как ведут себя модели при рабочем пороге уверенности.
Это **пилот**, а не полный бенчмарк: сцена синтетическая, объектов мало.

## Стенд

- Gazebo Sim 8.15.0, ROS 2 Jazzy, контейнер `walking_robot_sim`
  (`compose.yml`, сервис `simulator`), headless-рендер Ogre2.
- Камера: 640×480, HFOV 60°, 10 Гц, горизонтальная установка.
- Сцена: пять одинаковых стульев `aws_robomaker_residential_ChairA_01`
  из `src/gazebo_sim/models/`, четыре ракурса камеры.
- Ground truth: проекция 3D-габаритов стула на изображение по известной позе
  камеры и внутренним параметрам, с обрезкой по границам кадра.
- Инференс: Ultralytics 8.4.182, PyTorch 2.13 CPU, 16-ядерный CPU,
  8 потоков torch. Кадры сняты из Gazebo и обработаны offline.

## Результаты

20 объектов (5 стульев × 4 ракурса), `AP@0.5` — класс-агностичная.

| Модель | T, мс (медиана) | f, Гц | AP@0.5 | TP/FP/FN при conf ≥ 0.5 | Параметры, млн | Размер, МБ |
| --- | --- | --- | --- | --- | --- | --- |
| YOLOv8n | 19.3 | 51.9 | 0.995 | 11 / 0 / 9 | 3.16 | 6.55 |
| YOLO11n | 20.3 | 49.1 | 0.986 | 19 / 2 / 1 | 2.62 | 5.61 |
| YOLOv10n | 20.0 | 49.9 | 0.982 | 5 / 0 / 15 | 2.78 | 5.86 |

Максимальная уверенность: 0.741 / 0.872 / 0.753 соответственно.

## Что показывает пилот

1. Все три модели укладываются в ограничение `T ≤ 0.1 с` с большим запасом:
   фактическое время 19–20 мс против аналитических 66–89 мс. Аналитическая
   оценка через `Π = 100 Гоп./с` консервативна.
2. `AP@0.5` на простой синтетической сцене близок к насыщению у всех моделей,
   поэтому по нему модели неразличимы. Различия проявляются при рабочем
   пороге 0.5: YOLO11n находит 19 из 20 объектов, YOLOv8n — 11, YOLOv10n — 5.
3. YOLO11n даёт лучший компромисс: меньше всего параметров и размера,
   максимальная уверенность и почти полный recall при пороге 0.5.
   Это согласуется с выбором модели в статье, но не является его
   доказательством: сцена слишком простая.

## Ограничения

- Пять одинаковых объектов и четыре ракурса — недостаточно для устойчивой
  оценки mAP; числа AP следует читать как оценку сверху.
- GT построен по осевому 3D-AABB модели, а не по ручной разметке.
- Инференс выполнялся на хосте (venv `lyrical`), а не через ROS-узел
  `quadropted_perception/yolo_detector`: в контейнере сломан пакет
  `torchvision` (`PackageNotFoundError`).
- Штатный `cafe.world` с камерой робота не запускался: `launch_cpp.launch.py`
  поднимает GUI и полный Nav2-стек.

## Воспроизведение

```bash
# 1. Поднять симулятор
docker compose up -d simulator

# 2. Снять кадры (мир и позы — в world.sdf)
docker compose exec -T simulator bash -lc \
  'source /opt/ros/jazzy/setup.bash; python3 /root/ws/data/exp/capture.py 3 /root/ws/data/exp/frames/pose0'

# 3. Посчитать метрики
.venv-lyrical/bin/python data/gazebo/exp/eval_models.py
```

Файлы:

- `world.sdf` — сцена с камерой и стульями;
- `capture.py` — сохранение кадров из ROS-топика `/camera/image`;
- `eval_models.py` — GT-проекция, AP@0.5, замер T;
- `results.json` — сырые результаты;
- `frames/pose{0..3}/` — кадры.
