# Глава 3. Разработка модуля Elevation Mapping и terrain-aware планирования

## 3.11 Тестирование в симуляции Gazebo

Валидация разработанного модуля проводилась в симуляционной среде Gazebo Harmonic с использованием модели робота Unitree Go2. Для всесторонней проверки были созданы тестовые миры с различными типами рельефа, от простой ровной поверхности до сложных сценариев с множественными препятствиями. Каждый сценарий нацелен на проверку определённого аспекта системы: точности карты высот, корректности фильтрации, качества сегментации и адекватности планирования пути. Тестирование проводилось автоматически с сохранением метрик и логов для последующего анализа. В данном разделе описываются тестовые сценарии, процедура тестирования и полученные результаты.

### 3.11.1 Сценарии и процедура тестирования

Для валидации разработанного модуля созданы тестовые миры Gazebo с различными типами рельефа.

Сценарий 1 — ровная дорога (baseline): плоская поверхность без препятствий. Цель: проверка базовой работы. Ожидаемый результат: RMSE < 0,02 м, traversability = 1,0, скорость 0,5 м/с.

Сценарий 2 — лёгкие неровности (трава, гравий, камни 0,02–0,05 м). Цель: проверка ground segmentation. Ожидаемый результат: ground > 90%, traversability > 0,7, высота шага 0,04–0,08 м.

Сценарий 3 — холмы и подъёмы: синусоидальный рельеф с перепадами до 0,5 м:

$$
z(x, y) = A \sin(\omega_x x) \cos(\omega_y y), \quad A = 0.3\ \mathrm{м}
$$

Цель: проверка gradient и slope cost. Ожидаемый результат: planner выбирает путь через долины.

Сценарий 4 — смешанный рельеф (ровные участки, трава, камни, холмы). Цель: проверка terrain-aware планирования и адаптации походки. Ожидаемый результат: безопасный маршрут с адаптацией походки.

Сценарий 5 — препятствия (ящики, бордюры, ступени 0,1–0,3 м). Цель: проверка no-go зон. Ожидаемый результат: препятствия > 0,2 м классифицируются как Unsafe, остановка с запасом ≥ 0,3 м.

Для каждого сценария процедура включает: запуск симуляции с соответствующим миром, запуск elevation_mapping_node с RViz, запись rosbag. Робот выполняет движение по waypoints, записываются PointCloud2, elevation map, ground/obstacle облака, параметры походки, odometry и joint states. Критерии успеха: отсутствие ошибок ROS, RMSE в допуске, отсутствие экстренных остановок (кроме Scenario 5).

### 3.11.2 Результаты тестирования

Stage 0 — модульные тесты elevation_mapping_cupy: все 41 тестов пройдены, карта строится за < 2 мс на GPU, потребление памяти ~1,2 ГБ.

Stage 1 — Docker-интеграция: оба контейнера запускаются без ошибок, DDS discovery стабилен, TF-relay работает корректно.

Stage 2 — LiDAR → elevation_map pipeline: PointCloud2 принимается, карта публикуется с кадром odom, разрешением 0,1 м, частота 10 Гц.

Stage 3 — ground segmentation: на ровной поверхности precision > 98%, recall > 95%; на холмистой — precision > 95%, recall > 90%. Время обработки < 5 мс.

Stage 4 — traversability: gradient вычисляется корректно, классификация safe/medium/unsafe работает, cost map маркирует no-go зоны.

Stage 5 — адаптация походки: параметры изменяются плавно, робот останавливается перед no-go зоной.

Stage 6 — интеграция Nav2: исправлены QoS и map_topic в nav2_params.yaml. Frame shift odom/map остаётся открытой проблемой.

Stage 7 — одометрия: ground truth публикуется, stall detection работает. Выявлен дрейф leg odometry при проскальзывании.

### 3.11.3 Анализ ошибок и уроки

Наиболее частые ошибки, выявленные в ходе тестирования:

1. недостаточная точность на дальних расстояниях: на расстоянии более 8 м вертикальное разрешение LiDAR (шаг около 1,875°) даёт вертикальное разрешение около 26 см, что приводит к повышенной ошибке на удалённых участках карты;

2. потеря ground на крутых склонах (более 20°): Ground Plane Fitting с 3 итерациями может потерять часть ground-точек на крутых склонах — рекомендуется увеличить число итераций до 4–5 для сложного рельефа;

3. колебания параметров походки на границе Medium/Safe: при traversability ≈ 0,7 возможны колебания между режимами, решением является использование гистерезиса (разные пороги для повышения и понижения).

**Урок 1: Несоответствие QoS (RELIABLE vs BEST_EFFORT).** Gazebo публикует `/model/robot1_my_bot/pose` с профилем BEST_EFFORT. Если нода подписывается с RELIABLE, сообщения не доставляются. Аналогично, elevation_mapping_node публикует GridMap с RELIABLE + TRANSIENT_LOCAL, а elevation_to_costmap_node должен подписываться с тем же профилем. Решение: всегда проверять QoS-профиль publisher'ов при разработке подписчиков.

**Урок 2: Сдвиг costmap из-за статического map — odom.** При движении робота elevation map остаётся в odom, Nav2 ожидает costmap в map. Static_transform_publisher map — odom = (0,0,0) не обновляется при перемещении. Решение: удалить статический publisher, позволить Nav2 стартовать с identity transform.

**Урок 3: Дрейф leg odometry при проскальзывании.** Gazebo симулирует физическое взаимодействие ног с грунтом, допуская микропроскальзывание. Leg odometry интегрирует это проскальзывание, EKF fuse с IMU, и Nav2 получает дрейфующую позицию. Stall detection не срабатывает, когда робот стоит на месте (delta = 0, joints не движутся). На ровной поверхности дрейф минимален (< 0,01 м/с), на пересечённой местности — до 0,05 м/с. Решение: в симуляции использовать ground truth odometry как основной источник позиции, stall detection применять только для детекции коллизий.
