# Глава 3. Разработка модуля Elevation Mapping и terrain-aware планирования

## 3.4 Интеграция 3D LiDAR

### 3.4.1 Выбор источника данных

На начальном этапе прорабатывался вариант использования depth-камеры
для построения карты высот. Depth-камера обеспечивает плотное облако точек
с высоким разрешением, однако анализ выявил следующие проблемы:

- Gazebo Harmonic публикует depth image в формате `sensor_msgs/Image`,
  а не `PointCloud2`. Конвертация depth → PointCloud2 требует
  значительных вычислительных ресурсов.
- На GPU 4GB (GTX 1650 Ti) обработка depth-потока с разрешением 640×480
  даёт низкий FPS (менее 5 кадров/с).
- Depth-камера имеет ограниченный угол обзора (обычно 60–90°),
  что недостаточно для кругового обзора.

Было принято решение использовать 3D LiDAR (gpu_lidar) со следующими
преимуществами:

- Круговой обзор 360° (азимут), что обеспечивает полную карту
  окружающего пространства.
- 16 вертикальных лучей (диапазон ±15°), что даёт достаточное
  разрешение для построения DEM.
- Частота 10 Гц при дальности до 12 м.
- GPU-ускорение встроено в модель gpu_lidar Gazebo.

### 3.4.2 Конфигурация gpu_lidar в SDF

Конфигурация лидара задаётся в SDF-описании модели робота:

```xml
<sensor name="gpu_lidar" type="gpu_lidar">
  <pose>0.22 0 0.095 0 0 0</pose>
  <topic>scan</topic>
  <update_rate>10</update_rate>
  <lidar>
    <scan>
      <horizontal>
        <samples>360</samples>
        <resolution>1</resolution>
        <min_angle>-3.14159</min_angle>
        <max_angle>3.14159</max_angle>
      </horizontal>
      <vertical>
        <samples>16</samples>
        <resolution>1</resolution>
        <min_angle>-0.2618</min_angle>
        <max_angle>0.2618</max_angle>
      </vertical>
    </scan>
    <range>
      <min>0.05</min>
      <max>12.0</max>
      <resolution>0.01</resolution>
    </range>
  </lidar>
  <alwaysOn>1</alwaysOn>
  <visualize>true</visualize>
</sensor>
```

Параметры лидара:

- **Позиция**: (0.22, 0, 0.095) относительно base_link — на корпусе робота.
- **Горизонтальные лучи**: 360 (1° разрешение, полный круг).
- **Вертикальные лучи**: 16 (диапазон ±15°, ~1.875° между лучами).
- **Частота обновления**: 10 Гц.
- **Дальность**: 0.05–12 м с разрешением 0.01 м.

### 3.4.3 Проблема: Gazebo публикует LaserScan, нужен PointCloud2

Gazebo gpu_lidar публикует `gz.msgs.LaserScan` — сообщение, которое
представляет собой набор расстояний для каждой точки сканирования.
Даже с 16 вертикальными лучами, данные публикуются как плоский массив
в формате `ranges[360 * 16]`.

ROS 2 `sensor_msgs/LaserScan` не имеет полей `vertical_angle_min/max`,
поэтому при прямом бридже через ros_gz_bridge вертикальная информация
теряется — все 16×360 точек проецируются в 2D плоскость.

### 3.4.4 Реализация C++ конвертера

Для решения проблемы написан C++ конвертер `laser_to_cloud_converter.cc`.
Архитектура конвертера:

1. **Подключение к Gazebo Transport**:
   Используется `gz::transport::Node` для подписки на топик `/scan`
   напрямую через libgz-transport (без бриджа).

2. **Обработка LaserScan**:
   При получении сообщения `gz.msgs.LaserScan`:
   - Извлекаются параметры сканирования (углы, количество лучей).
   - Восстанавливаются вертикальные углы: для 16 лучей диапазон
     ±15° разбивается равномерно.
   - Каждая точка проецируется в 3D:
     ```
     x = d * cos(θ_v) * sin(θ_h)
     y = d * cos(θ_v) * cos(θ_h)
     z = d * sin(θ_v)
     ```

3. **Публикация PointCloudPacked**:
   - Результат публикуется как `gz.msgs.PointCloudPacked`.
   - ros_gz_bridge автоматически конвертирует PointCloudPacked
     в `sensor_msgs/PointCloud2` на топик `/robot1/scan/points`.

4. **Обработка пределов**:
   - Точки с расстоянием < min (0.05 м) или > max (12 м) отбрасываются.
   - Точки с нулевым расстоянием (нет данных) отбрасываются.

### 3.4.5 Калибровка и проверка

Для проверки корректности конвертера используется тестовый скрипт,
который сравнивает количество точек в облаке с ожидаемым:

- Ожидаемое количество точек: 360 × 16 = 5760 (в идеальных условиях).
- Фактическое количество: зависит от видимых объектов (обычно 3000–5500).
- Для пустой плоскости: все 5760 точек возвращаются.

Для визуальной проверки используется RViz — облако точек отображается
поверх модели робота, и оценивается качество проецирования.

### 3.4.6 Ограничения

Выявленные ограничения подхода:

1. **Разрешение по вертикали**: 16 лучей с шагом ~1.875° дают
   разрешение ~3.3 см на расстоянии 1 м, но ~33 см на расстоянии 10 м.
   Это ограничивает точность DEM на дальних дистанциях.

2. **Слепые зоны**: над роботом (выше +15°) и под роботом (ниже -15°)
   данные отсутствуют. Необходимо следить за тем, чтобы эти зоны
   не содержали критически важных препятствий.

3. **Шум измерений**: gpu_lidar в Gazebo не моделирует шум реальных
   лидаров. При переходе на реальный LiDAR (Ouster, Velodyne) потребуется
   дополнительная фильтрация шума.

### 3.4.7 Альтернативы и перспективы

В качестве перспективного направления рассматривается использование
данных с нескольких сенсоров:

- **3D LiDAR + depth camera**: лидар обеспечивает круговой обзор,
  depth-камера — детальную карту непосредственно перед роботом.
- **Stereo vision**: две камеры для оценки глубины на близких
  дистанциях (до 3-5 м).
- **IMU + LiDAR odometry**: для уточнения положения робота между
  сканами лидара (LiDAR SLAM).
