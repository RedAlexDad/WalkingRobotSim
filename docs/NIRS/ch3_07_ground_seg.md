# Глава 3. Разработка модуля Elevation Mapping и terrain-aware планирования

## 3.7 Ground segmentation

### 3.7.1 Постановка задачи

Для корректного построения карты высот необходимо разделить облако точек на два класса: ground-точки (принадлежат поверхности земли, используются для обновления карты высот DEM) и non-ground точки (принадлежат препятствиям, объектам, нависающим структурам, используются для идентификации no-go зон).

Задача ground segmentation (сегментации поверхности земли) является классической проблемой обработки данных LiDAR [2]. Основные сложности: рельеф может быть неровным (холмы, овраги), что делает простой пороговый фильтр по z-координате неприменимым; наличие наклонных поверхностей (пандусы, склоны), которые являются проходимыми, но не являются строго горизонтальными; шум измерений, создающий ложные ground-точки.

### 3.7.2 Алгоритм Ground Plane Fitting

Выбран алгоритм Ground Plane Fitting (GPF), описанный в работе Зермаса и соавторов [2], адаптированный для ROS 2 Jazzy. Алгоритм состоит из следующих шагов.

Шаг 1 — подготовка данных: входное облако точек преобразуется из формата PointCloud2 в массив numpy (N, 3) с координатами (x, y, z).

Шаг 2 — фильтрация по высоте: отбрасываются точки выше max_height (0,5 м) и ниже min_height (–0,5 м) относительно сенсора.

Шаг 3 — воксельная фильтрация (voxel_downsample): для повышения производительности выполняется воксельное понижение разрешения с размером вокселя 0,05 м. Это сокращает количество точек с ~20 000 до 500–2000 без существенной потери информации о рельефе.

Шаг 4 — выбор кандидатов для начальной плоскости: из отфильтрованного облака выбираются точки с наименьшей z-координатой (нижние 20%). Это увеличивает вероятность того, что выбранные точки принадлежат ground, а не препятствиям.

Шаг 5 — итеративная подгонка плоскости (RANSAC): для каждой из max_iterations (3) итераций случайно выбираются 3 точки из нижних 20%, через них проводится плоскость $\mathbf{n} \cdot \mathbf{x} + d = 0$, вычисляется расстояние от каждой точки облака до плоскости. Точки с distance < distance_threshold_i считаются inliers (ground). На каждой итерации порог увеличивается: итерация 1 — 0,15 м, итерация 2 — 0,25 м, итерация 3 — 0,35 м.

Увеличение порога на каждой итерации позволяет захватывать неровный рельеф: первая итерация находит «ядро» плоскости, последующие присоединяют точки с отклонениями.

Шаг 6 — пост-фильтр height_margin после GPF: так как порог dist_threshold = 0,15 м на первой итерации может превышать высоту LiDAR над землёй (0,095 м), точки корпуса робота на уровне z ≈ 0 могут быть ошибочно классифицированы как ground. Для исключения таких артефактов применяется пост-фильтр: точки, высота которых превышает среднюю высоту ground более чем на height_margin = 0,05 м, перемещаются в obstacle облако.

Шаг 7 — skip-frame при перегрузке: если предыдущий кадр ещё обрабатывается, новый кадр пропускается (skip). Это предотвращает накопление очереди коллбэков с устаревшими TF-трансформациями, которое привело бы к дрейфу карты.

Шаг 8 — формирование результата: inliers (близкие к плоскости) формируют ground_cloud, outliers (далёкие от плоскости) — obstacle_cloud.

### 3.7.3 Проблема парсинга PointCloud2

При разборе сообщений PointCloud2 от ros_gz_bridge выяснилось, что стандартный `read_points()` из ROS 2 (C++) не работает для сообщений от Gazebo из-за нестандартного расположения полей. Для решения разработана функция `_read_xyz32`, которая:
— читает сырой буфер msg.data как numpy array uint8 и переформировывает в матрицу (N, point_step);
— строит offset-карту по полям (x, y, z): для каждого поля берётся его offset из msg.fields;
— извлекает координаты через индекс по смещению с приведением к float32.

Данный подход работает независимо от наличия дополнительных полей (intensity, ring, timestamp) и от порядка их расположения в сообщении.

### 3.7.4 Интеграция с elevation_mapping

Ground-облако подаётся на вход elevation_mapping_node вместо полного облака точек. Это обеспечивает: чистую карту высот (на карту попадают только точки поверхности земли, без влияния препятствий), корректную traversability (non-ground точки маркируются как препятствия и учитываются в cost map) и раздельную частоту обработки (ground может обновляться на каждом кадре с частотой 10 Гц, в то время как obstacle map может накапливаться за несколько кадров для снижения шума).

Obstacle-облако также подаётся на вход elevation_mapping_node в качестве второго входа: точки obstacles увеличивают дисперсию (variance) соответствующих ячеек карты и влияют на traversability (cost повышается). Для подписки на obstacle_cloud в конфигурации `go2_lidar3d.yaml` указан второй subscriber с топиком `/obstacle_cloud`.

### 3.7.5 Альтернативные алгоритмы

Для сравнения рассмотрены следующие альтернативы:

— GPF (Ground Plane Fitting) — выбранный алгоритм. Преимущества: быстрый, простой в реализации, работает на неровном рельефе. Недостатки: не работает на вертикальных поверхностях (стены).

— RANSAC с одной плоскостью: очень быстрый (1 итерация), но не захватывает неровный рельеф, теряет ground на холмах.

— Ray-based filtering (Patchwork): сегментирует даже на сложном рельефе, но требует больше ресурсов и сложнее в настройке [12].

— LineFit: эффективен для разреженных облаков, но требует упорядоченного облака (по строкам сканирования).

### 3.7.6 Метрики качества сегментации

Для оценки качества ground segmentation используются метрики: precision (доля истинных ground среди предсказанных ground, целевое значение > 95%), recall (доля найденных ground-точек от всех ground, > 90%), F1-score (гармоническое среднее precision и recall, > 0,92), FP rate (доля non-ground, ошибочно отнесённых к ground, < 5%).

Для получения ground truth в симуляции Gazebo создаётся дополнительное облако точек, содержащее только поверхность земли (без препятствий), и сравнивается с результатом сегментации.
