# Глава 3. Разработка модуля Elevation Mapping и terrain-aware планирования

## 3.11 Тестирование в симуляции Gazebo

### 3.11.1 Сценарии тестирования

Для валидации разработанного модуля созданы тестовые миры Gazebo с различными типами рельефа.

Сценарий 1 — ровная дорога (baseline): плоская поверхность без препятствий (z = const). Цель: проверка базовой работы elevation mapping, фильтрации тела робота и корректности TF-трансформаций. Ожидаемый результат: RMSE карты высот < 0,02 м, все 5760 точек LiDAR корректно проецируются, traversability = 1,0 для всех ячеек, робот движется с максимальной скоростью 0,5 м/с.

Сценарий 2 — лёгкие неровности: поверхность с мелкими неровностями (трава, гравий, мелкие камни высотой 0,02–0,05 м). Цель: проверка ground segmentation и базовой traversability. Ожидаемый результат: ground segmentation выделяет более 90% точек как ground, traversability > 0,7, высота шага = 0,04–0,08 м.

Сценарий 3 — холмы и подъёмы: синусоидальный рельеф с перепадами высот до 0,5 м, описываемый функцией z(x, y) = A × sin(ω_x × x) × cos(ω_y × y) с параметрами A = 0,3 м, ω_x = ω_y = 0,5 рад/м. Цель: проверка gradient и slope cost. Ожидаемый результат: gradient корректно вычисляется для наклонных поверхностей, slope cost пропорционален углу наклона, planner выбирает путь через долины между холмами.

Сценарий 4 — смешанный рельеф: комбинация ровных участков, травы, камней и холмов. Цель: проверка terrain-aware планирования и адаптации походки в комплексном сценарии. Ожидаемый результат: planner выбирает безопасный маршрут с учётом рельефа, походка адаптируется при смене типа поверхности, робот огибает непроходимые участки.

Сценарий 5 — препятствия: ящики, бордюры, ступени высотой 0,1–0,3 м. Цель: проверка обнаружения no-go зон и корректной классификации. Ожидаемый результат: препятствия высотой более 0,2 м классифицируются как Unsafe, робот останавливается перед препятствием с запасом не менее 0,3 м.

### 3.11.2 Процедура тестирования

Для каждого сценария выполняется следующая процедура. Подготовка: запуск симуляции Gazebo с соответствующим миром, запуск elevation_mapping_node с RViz для визуализации, настройка записи rosbag. Выполнение: робот выполняет движение по заданному маршруту (набор waypoints), во время движения записываются PointCloud2 от LiDAR, elevation map (GridMessage), ground/obstacle облака, параметры походки, odometry и joint states. Анализ: воспроизведение rosbag, вычисление метрик качества, визуальный анализ в RViz.

Критерии успеха: отсутствие ошибок в ROS-нодах, RMSE карты высот в пределах допуска, отсутствие экстренных остановок (кроме Scenario 5), корректное обнаружение no-go зон.

### 3.11.3 Результаты тестирования

Stage 0 — валидация elevation_mapping_cupy (модульные тесты): все 41 модульных тестов пакета elevation_mapping_cupy пройдены, synthetic depth demo работает корректно, карта высот строится за менее чем 2 мс на GPU, потребление GPU-памяти составляет около 1,2 ГБ из 4 ГБ доступных.

Stage 1 — Docker-интеграция: оба контейнера собираются и запускаются без ошибок, Cyclone DDS discovery работает стабильно с отключённым SHM, TF-relay корректно передаёт трансформации между контейнерами, RViz в GPU-контейнере отображает все топики.

Stage 2 — LiDAR  —  elevation_map pipeline: PointCloud2 от LiDAR успешно принимается elevation_mapping_node, elevation map публикуется с кадром odom и разрешением 0,1 м, слои elevation, variance, traversability обновляются на каждом кадре, фильтрация тела робота (min_valid_distance = 0,3) исключает артефакты, частота публикации стабильно составляет 10 Гц.

Stage 3 — ground segmentation: Ground Plane Fitting корректно разделяет облако точек, на ровной поверхности precision > 98%, recall > 95%, на холмистой поверхности precision > 95%, recall > 90%, время обработки составляет менее 5 мс на кадр (CPU, Python + numpy).

Stage 4 — traversability: gradient корректно вычисляется для наклонных поверхностей, классификация safe/medium/unsafe работает в соответствии с заданными порогами, cost map корректно маркирует препятствия как no-go зоны.

Stage 5 — адаптация походки: параметры походки изменяются при смене типа поверхности, переходы между режимами плавные (экспоненциальное сглаживание), робот корректно останавливается перед no-go зоной.

Stage 6 — интеграция Nav2 через costmap bridge: elevation_to_costmap_node конвертирует GridMap в OccupancyGrid. Выявлены и исправлены проблемы: несоответствие QoS (RELIABLE + VOLATILE  —  TRANSIENT_LOCAL), неправильное имя параметра в nav2_params.yaml (topic  —  map_topic). Frame shift между odom и map остаётся открытой проблемой (см. анализ ниже).

Stage 7 — анализ одометрии: ground_truth_publisher успешно публикует эталонную одометрию от Gazebo, stall detection корректно идентифицирует остановки робота (угловая скорость < 0,05 рад/с при движении суставов), QoS для подписки на Gazebo /model/robot1_my_bot/pose исправлен с RELIABLE на BEST_EFFORT. Выявлена проблема дрейфа leg odometry: при движении по неровной поверхности Gazebo допускает физическое проскальзывание ног, что интегрируется в leg odometry и через EKF попадает в Nav2, вызывая планирование в неверной позиции.

### 3.11.6 Анализ ошибок и уроки

Наиболее частые ошибки, выявленные в ходе тестирования:

1) недостаточная точность на дальних расстояниях: на расстоянии более 8 м вертикальное разрешение LiDAR (шаг около 1,875°) даёт вертикальное разрешение около 26 см, что приводит к повышенной ошибке на удалённых участках карты;

2) потеря ground на крутых склонах (более 20°): Ground Plane Fitting с 3 итерациями может потерять часть ground-точек на крутых склонах — рекомендуется увеличить число итераций до 4–5 для сложного рельефа;

3) колебания параметров походки на границе Medium/Safe: при traversability ≈ 0,7 возможны колебания между режимами, решением является использование гистерезиса (разные пороги для повышения и понижения).

**Урок 1: Несоответствие QoS (RELIABLE vs BEST_EFFORT).** Gazebo публикует `/model/robot1_my_bot/pose` с профилем BEST_EFFORT. Если нода подписывается с RELIABLE, сообщения не доставляются. Аналогично, elevation_mapping_node публикует GridMap с RELIABLE + TRANSIENT_LOCAL, а elevation_to_costmap_node должен подписываться с тем же профилем. Решение: всегда проверять QoS-профиль publisher'ов при разработке подписчиков.

**Урок 2: Сдвиг costmap из-за статического map — odom.** При движении робота elevation map остаётся в odom, Nav2 ожидает costmap в map. Static_transform_publisher map — odom = (0,0,0) не обновляется при перемещении. Решение: удалить статический publisher, позволить Nav2 стартовать с identity transform.

**Урок 3: Дрейф leg odometry при проскальзывании.** Gazebo симулирует физическое взаимодействие ног с грунтом, допуская микропроскальзывание. Leg odometry интегрирует это проскальзывание, EKF fuse с IMU, и Nav2 получает дрейфующую позицию. Stall detection не срабатывает, когда робот стоит на месте (delta = 0, joints не движутся). На ровной поверхности дрейф минимален (< 0,01 м/с), на пересечённой местности — до 0,05 м/с. Решение: в симуляции использовать ground truth odometry как основной источник позиции, stall detection применять только для детекции коллизий.
