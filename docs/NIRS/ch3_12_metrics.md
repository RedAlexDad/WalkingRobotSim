# Глава 3. Разработка модуля Elevation Mapping и terrain-aware планирования

## 3.12 Оценка качества и метрики

### 3.12.1 Метрики точности карты высот

Для количественной оценки качества построенной карты высот используются стандартные метрики регрессии.

RMSE (Root Mean Square Error): RMSE = sqrt((1/N) × Σ(z_predicted − z_ground_truth)²). RMSE чувствителен к крупным ошибкам, штрафует выбросы квадратично. Целевое значение: < 0,05 м (5 см).

MAE (Mean Absolute Error): MAE = (1/N) × Σ|z_predicted − z_ground_truth|. MAE — средняя абсолютная ошибка, менее чувствительна к выбросам. Целевое значение: < 0,03 м (3 см).

Max Error: Max Error = max|z_predicted − z_ground_truth| — максимальное отклонение, показатель худшего случая. Целевое значение: < 0,10 м (10 см).

Coverage: Coverage = N_valid / N_total × 100% — процент ячеек карты, для которых есть хотя бы одно измерение. Целевое значение: > 90% после 10 секунд сканирования.

Ground truth для тестовых миров Gazebo получается из аналитической функции высоты z = f(x, y). Для Scenario 1: z = const (0). Для Scenario 3: z = A × sin(ω_x × x) × cos(ω_y × y). Для Scenario 4: комбинация функций с кусочной интерполяцией.

### 3.12.2 Метрики производительности

FPS карты (Frame Rate) — частота обновления elevation map на выходе ноды. Целевое значение: ≥ 10 Гц (соответствует частоте LiDAR). Измерение: количество сообщений `/elevation_map` за 10 секунд, делённое на 10.

Latency (задержка) — время от получения PointCloud2 до публикации обновлённой elevation map: latency = t_publish − t_receive_pointcloud. Целевое значение: < 100 мс. Измерение: сравнение временных меток входящего PointCloud2 и исходящего GridMessage.

GPU memory usage — пиковое использование GPU-памяти в процессе работы. Целевое значение: < 2 ГБ (из 4 ГБ доступных на GTX 1650 Ti). Измерение: `nvidia-smi` в процессе работы.

CPU usage — загрузка CPU в elevation-контейнере (не включая GPU-вычисления). Целевое значение: < 50%. Измерение: `htop` или `docker stats` в процессе работы.

### 3.12.3 Метрики одометрии

Для оценки качества одометрии введены дополнительные метрики:

— дрейф позиции: средняя ошибка положения относительно ground truth: drift = (1/N) × Σ||pos_odom − pos_gt||. Целевое значение: < 0,05 м/с. Измерение: сравнение /odom и /robot1/ground_truth;

— stall detection accuracy: TP/(TP + FN) — доля корректно обнаруженных остановок. Целевое значение: > 95%;

— latency stall detection: задержка между фактической остановкой и публикацией /stall_status = true. Целевое значение: < 200 мс;

— ground truth availability: процент времени, когда ground truth odometry доступна. Целевое значение: > 99%.

### 3.12.4 Метрики производительности CPU

Для CPU-режима (Dockerfile.cpu) измеряются дополнительные метрики:

— частота обновления карты, Гц — целевое значение: ≥ 5 Гц;

— загрузка CPU, % — целевое значение: < 80%.

### 3.12.5 Метрики навигации

Для оценки эффективности навигации используются следующие метрики:

— длина пути: фактическая длина траектории робота от A до B, сравнение baseline (без terrain-awareness) и terrain-aware;

— время прохождения: время от старта до финиша по заданному маршруту;

— средняя скорость: v_avg = path_length / travel_time;

— энергозатраты: интегральная мощность приводов за время движения: energy = Σ(τ_i × ω_i × Δt), где τ_i — момент i-го привода, ω_i — угловая скорость i-го привода, измерение из joint_states;

— количество остановок: количество экстренных остановок в no-go зонах (в идеале 0 — все препятствия должны быть обнаружены заранее).

### 3.12.6 Инструменты сбора метрик

Для автоматического сбора метрик разработан скрипт `compute_metrics.py`, который включает функции read_rosbag (чтение топиков /elevation_map, /ground_truth, /odom, /joint_states), compute_height_metrics (RMSE, MAE, Max Error, Coverage), compute_performance_metrics (FPS, Latency, GPU/CPU usage) и compute_navigation_metrics (длина пути, время, средняя скорость, энергозатраты, количество остановок). Результаты сохраняются в CSV-файл для последующего анализа.

### 3.12.7 Сравнение с baseline

Для оценки эффективности terrain-aware подхода проводится сравнение с baseline-режимом. Baseline использует построение двумерной costmap только на основе загруженности (occupancy), фиксированные параметры походки (step_height = 0,04 м, frequency = 2,0 Гц) и кратчайший путь A* без учёта рельефа [3]. Terrain-aware режим использует traversability costmap с учётом рельефа, адаптивные параметры походки и выбор пути с учётом безопасности.

Ожидаемые результаты сравнения: terrain-aware — меньший RMSE карты (на 10–20%), меньшее количество остановок (на 50–100%), меньшие энергозатраты (на 15–25%); baseline — меньшее время прохождения (на 10–20%), но больше рисков.
