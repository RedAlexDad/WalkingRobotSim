# rl_sar: телеметрия (CSV) и нестабильность DDS

**Дата:** 2026-10-09
**Ветка:** `feat/rl-sar`
**Контекст:** попытка собрать телеметрию RL-походки Go2 в Gazebo и сравнить
с модельным контроллером.

---

## 1. Телеметрия: что было и что сделано

**Было (штатный CSV-логгер rl_sar):** 60 колонок — на каждый из 12
суставов: `tau_cal`, `tau_est`, `joint_pos`, `joint_pos_target`,
`joint_vel`. Логгер выключен (`// #define CSV_LOGGER`), файл пишется в
каталог политики.

**Сделано (в исходниках rl_sar, в контейнере):**
1. Включён логгер (`#define CSV_LOGGER` в `rl_sim.hpp`).
2. Логгер **расширен** без смены сигнатур (доп. столбцы берутся из полей
   класса): добавлены
   - `time` (модельное время),
   - `cmd_x`, `cmd_y`, `cmd_yaw` (команда),
   - `quat_w,x,y,z` (ориентация из IMU),
   - `gyro_x,y,z` (угловая скорость),
   - `act_0..11` (выход политики).
   Итого ≈ **78 колонок** (60 + 15). Каталог вывода изменён на `/tmp`
   (каталог политики смонтирован read-only).
3. Сборка пакета прошла успешно (`colcon build --packages-select rl_sar`),
   при запуске заголовок CSV создаётся.

> Данные строк не набираются, пока `rl_sim` не начнёт реально исполнять
> политику (см. п.2 — запуск блокируется).

## 2. Нестабильность ROS 2 DDS (блокер)

Наблюдение: `rl_sim` при старте поднимает собственный контроллер
`robot_joint_controller` через `controller_manager`. Это **не всегда
получается**:

- `Could not contact service /controller_manager/list_controllers`
  (discovery не находит `controller_manager`);
- `Failed getting a result from calling /controller_manager/...`
  (сервис найден, но вызов не проходит);
- FastDDS SHM: `Failed init_port fastrtps_port7427: open_and_lock_file
  failed` (`/dev/shm` 64 МБ; перемонтирование до 2 ГБ не помогло —
  проблема в блокировке порта, не в объёме).

Что пробовали:

| Мера | Результат |
|---|---|
| Остановка второго контейнера (`ipc: host`) | не помогло |
| Очистка `/dev/shm/fastrtps_*`, `sem.*` | не помогло |
| Профиль FastDDS **UDP-only** | иногда проходит, чаще нет |
| Default transport (SHM+UDP) | ошибки SHM-порта |
| `ROS_LOCALHOST_ONLY=1` | не помогло |
| Отдельный `ROS_DOMAIN_ID` | не помогло |
| Перемонтирование `/dev/shm` 2 ГБ | не помогло |
| Цикл «чистый запуск → rl_sim» ×3 | все три — блокировка |

**Важно:** один прогон **ранее удался** — робот встал и прошёл ≈3.4 м
(см. `docs/rl-sar/README.md`). То есть стек рабочий, но **запуск
нестабилен** из-за DDS в этом окружении.

## 3. Что нужно для стабильной телеметрии

1. Надёжный DDS: явный профиль FastDDS с одним интерфейсом, либо
   `rmw_cyclonedds` с конфигом, либо увеличенный SHM + корректные
   lock-файлы.
2. Либо обойти discovery: поднимать `robot_joint_controller` заранее и
   патчить `rl_sim`, чтобы он не падал, если контроллер уже активен
   (сейчас — падает).
3. После стабилизации — гонять серии (RL vs модельный TROT/IK) и снимать
   расширенный CSV.

## 4. Сравнение RL и TROT/IK (план)

- **RL:** rl_sar `rl_sim` (политика `himloco`/`robot_lab`).
- **TROT/IK:** отдельный узел, который считает trot-походку + обратную
  кинематику и публикует команды в тот же `robot_joint_controller`
  (тот же интерфейс и гейны → честное сравнение в одной среде).
- **Телеметрия:** расширенный CSV (см. п.1) для обоих режимов.
- **Метрики:** скорость, высота корпуса и её разброс, крен/тангаж, дрейф,
  удельные затраты, падения.

## 5. Итог

- Разбор телеметрии выполнен; логгер включён и расширен (≈78 колонок).
- Полноценный сбор данных и сравнение **заблокированы нестабильностью
  DDS** в контейнере; единичный успешный прогон показывает, что стек
  работоспособен.
- Для продолжения нужно стабилизировать DDS (см. п.3).
