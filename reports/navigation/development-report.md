# Отчёт о доработке навигации и ИМ оператора в RViz

Промежуточный технический отчёт: эксплуатационные проблемы, выдвинутые гипотезы (принятые и отвергнутые с обоснованием), методы решения и результат.

- Проект: `WalkingRobotSim`
- Ветка: `feat/ergonomics-rviz-demo`
- Дата: 2026-10-27
- Среда: Ubuntu, GNOME/Wayland (X11-приложения через Xwayland), ROS 2 Jazzy в контейнере `walking_robot_sim`, RViz 2 на хосте (ROS 2 Lyrical), Gazebo Harmonic (`gz sim` 8), GPU AMD Radeon 780M
- Дисплей: eDP 3456×2160 (≈290 PPI), HDMI 5120×2880
- Проверочная сцена: `cafe.world`, карта `cafe_world_map` 191×447 при 0,05 м/пикс, 8 waypoints из `default.yaml`

---

## 1. Постановка

Требовалось получить воспроизводимый запуск симуляции с нужным RViz одной командой и ИМ оператора, которая показывает **реальное состояние системы**, а не нарисованную картинку:

1. запуск: `make gazebo RVIZ=ergonomic` без ручных `docker cp` и двух терминалов;
2. waypoints в ИМ — из коллектора, а не из YAML;
3. поза робота — из одометрии, а не из номера waypoint;
4. препятствия — контурами, а не точками;
5. 30 FPS и отсутствие мерцания;
6. жёсткое правило: окно с мерцанием не должно выводиться на экран.

До работы было: `RVZ=false|true` (булев флаг), ИМ рисовала 8 waypoints из файла независимо от состояния коллектора, робот «ехал» по waypoint'ам при смене состояния, препятствие было точкой в демо-состоянии, RViz в контейнере шёл через software GL.

---

## 2. Методика разбора

Для каждой проблемы формулировалось несколько конкурирующих гипотез. Каждая проверялась минимальным экспериментом: `ros2 topic echo/info/hz`, `tf2_echo`, сравнение скриншотов окна покадрово, чтение статусбара RViz, логи launch и коллектора.

Гипотеза **отвергалась**, если эксперимент давал несовместимый результат: сообщение об ошибке, отсутствие ожидаемого эффекта, регресс. Гипотеза **принималась**, если её следствие устойчиво воспроизводилось.

Ключевой инструмент — покадровое сравнение окна RViz: сцена на старте статична, поэтому доля изменившихся пикселей между соседними кадрами прямо измеряет мерцание. Для этого написан `scripts/check_flicker.py`.

## 3. Проблемы, гипотезы и решения

### П-1. Штатный RViz роняет симуляцию (серьёзность высокая)

**Проблема.** `make gazebo` запускал RViz внутри launch; RViz падал с `terminate called without an active exception`, а launch считал его обязательным процессом и завершал всю симуляцию.

**Гипотезы:**

- **H1. Дефект конкретного `.rviz`-конфига.** — *Отвергнута.* Падение воспроизводилось при разных конфигах и без конфига.
- **H2. Несовместимость GL-контекста RViz с окружением контейнера.** — *Принята частично.* RViz в контейнере нестабилен, но сама симуляция без него работает.
- **H3. Достаточно отключить RViz в launch.** — *Принята как обход.* `RVZ=false` убирал падающий процесс, симуляция поднималась.

**Решение.** Штатный RViz не используется; симуляция запускается с `enable_rviz:=false`, ИМ поднимается отдельным процессом.

**Итог.** Симуляция живёт, ИМ управляется независимо.

---

### П-2. `RVZ` — булев флаг, он не тянет конфиг

**Проблема.** Требовалось `make gazebo RVIZ=ergonomic`, но переменная `RVZ` принимала только `true/false` и передавалась в `enable_rviz`.

**Гипотезы:**

- **H1. Добавить отдельный флаг под каждую ИМ.** — *Отвергнута.* Плодит комбинации и не покрывает произвольные конфиги.
- **H2. Один аргумент `RVIZ`, принимающий режим или путь.** — *Принята.* Значения: `default`, `false`, `ergonomic`, `<путь>.rviz`.

**Решение.**
- `RVIZ=default|true` — штатный RViz из launch;
- `RVIZ=false|none|off|0` — без RViz;
- `RVIZ=ergonomic` — внешний RViz с ИМ + издатель + коллектор;
- `RVIZ=<путь>` — любой конфиг, RViz стартует отдельно;
- `RVZ=false` оставлен алиасом;
- добавлен `SLAM=False` для переключения на AMCL;
- цель `rviz-kill` для уборки осиротевших процессов.

**Итог.** `make gazebo RVIZ=ergonomic` работает. Коммит `8a296e8`.

---

### П-3. 1–3 FPS в RViz

**Проблема.** Сцена обновлялась рывками; работать и снимать скриншоты невозможно.

**Гипотезы:**

- **H1. Тяжёлая сцена: карта 191×447, десятки маркеров.** — *Отвергнута.* Та же сцена на хосте выдавала 31 FPS.
- **H2. RViz в контейнере рендерит через software GL.** — *Принята.* В пресете стоял `LIBGL_ALWAYS_SOFTWARE=1` (добавлен ранее как обход чёрного окна). При этом CPU-рендеринг 3456×2160 физически не даёт 30 FPS.

**Решение.** RViz запускается на хосте с аппаратным GL; `LIBGL_ALWAYS_SOFTWARE` убран; добавлен `RVIZ_HOST_DISTRO ?= lyrical` (на хосте ROS 2 Lyrical, в контейнере Jazzy).

**Итог.** Статусбар RViz: **31 FPS** (окно 3200×1800). Коммиты `8a296e8`, `24085cb`, `552c4a4`.
*Оговорка:* точный FPS в software-режиме инструментально не снимался — фиксировалось только наблюдаемое обновление рывками.

---

### П-4. Мерцание: чёрные кадры и «дышащее» окно

**Проблема.** Окно периодически становилось чёрным; область вида то увеличивалась, то уменьшалась; колесо мыши не меняло масштаб.

**Гипотезы:**

- **H1. Массовые `DELETE` маркеров каждый цикл.** — *Принята частично.* Издатель присылал `DELETE` на все id (64 для waypoints, 32 для препятствий), затем снова `ADD`. Слои мигали с частотой публикации. Это даёт мигание слоёв, но не почернение всего окна.
- **H2. Swap под Xwayland при включённом vsync.** — *Принята.* Бисекция: с остановленным издателем 0 % изменений между кадрами, с работающим — 93 % (чёрные кадры). С `vblank_mode=0 __GL_SYNC_TO_VBLANK=0` — 0,38 % (ниже порога).
- **H3. Окно борется с WM за размер.** — *Принята.* В конфиге был прописан `Window Geometry 1920×1080`, запуск шёл то с `--fullscreen`, то с `--qwindowgeometry`, то с `wmctrl -e`. Плюс в конфиге дублировался блок `Tools`. Отсюда «площадь то растёт, то уменьшается» и неработающий зум.

**Решение.**
1. Удаляются только хвостовые id, когда список сокращается; полный свип — один раз на старте.
2. RViz: один экземпляр, `vblank_mode=0 __GL_SYNC_TO_VBLANK=0`.
3. Конфиг почищен: один блок `Tools` (`MoveCamera`, `Select`), корректный `Window Geometry`.
4. Добавлены `scripts/check_flicker.py` и цель `flicker-check`; пресет проверяет окно после старта и **закрывает его**, если переход между кадрами выше 0,5 %.

**Итог.** 10 кадров, худший переход 0,38 %, плохих 0. Коммиты `371c826`, `552c4a4`.

### П-5. Коллектор висит на `amcl/get_state`

**Проблема.** `make waypoint-start` возвращал `Nav2 is not ready yet`; коллектор бесконечно ждал `amcl/get_state`, хотя launch поднимает `slam_toolbox`.

**Гипотезы:**

- **H1. Nav2 не поднялся.** — *Отвергнута.* Lifecycle-узлы активны, `controller_server` и `planner_server` в `active`.
- **H2. `BasicNavigator.waitUntilNav2Active()` по умолчанию ждёт AMCL.** — *Принята.* В режиме SLAM сервиса `amcl` нет; ожидание не завершается.

**Решение.** Параметр `localizer` (по умолчанию `slam_toolbox`), передаётся в `waitUntilNav2Active`.

**Итог.** В логе `Nav2 is ready for use!`, `Nav2 is active`. Коммит `8636997`.

---

### П-6. ИМ рисует waypoints, которых в системе нет

**Проблема.** До `load_waypoints` коллектор имел пустой список, а в RViz уже было 8 точек. Это ложное представление плана.

**Гипотезы:**

- **H1. RViz кэширует старые маркеры.** — *Отвергнута.* Маркеры публиковались заново при каждом запуске.
- **H2. Источник waypoints — файл `default.yaml`, а не коллектор.** — *Принята.* `im_publisher` читал YAML и не знал о состоянии коллектора.

**Решение.** Коллектор публикует `/waypoint_state` (`std_msgs/String`, JSON): `count`, `active`, `current`, координаты. Издатель подписан на него (`source:=ros`); пока список пуст — ни точек, ни пути, `WP: NONE`.

**Итог.**

| Шаг | `/waypoint_state` | На экране |
|---|---|---|
| до загрузки | `count=0, active=false` | точек нет, `WP: NONE` |
| `make waypoint-load FILE=default.yaml` | `count=8, active=false` | 8 серых, `WP: 8 LOADED` |
| `make waypoint-start` | `count=8, active=true, current=0` | `WP: 1 -> 2`, цель 1 оранжевая, 2 синяя |

Коммиты `8636997`, `747f612`.

### П-7. Маркер робота ехал по waypoint, а не по позе

**Проблема.** Робот стоял на спавне, а в RViz перемещался при смене состояния ИМ.

**Гипотезы:**

- **H1. Глюк RViz.** — *Отвергнута.* Позиция маркера однозначно задавалась издателем.
- **H2. `publish_robot` берёт координаты `current_id`, а состояние `confirmed` переключало пару 8→1.** — *Принята.* Это и давало «телепорт».

**Решение.** Поза берётся из `/robot1/odom` (x, y, yaw); `confirmed` больше не двигает робота и не переключает пару; переключение — только по факту прибытия.

**Итог.** Проверка: робот сдвинут командой `/robot1/cmd_vel` на 0,73 м, footprint ушёл ровно на 0,73 м (`0,013 → 0,733` по `/odom`), waypoint 8 осталась на месте. Коммит `747f612`.

### П-8. Препятствие точкой

**Проблема.** В состоянии `stuck` препятствие рисовалось сферой; в остальных состояниях препятствий не было вовсе.

**Гипотезы:**

- **H1. Точки достаточно.** — *Отвергнута.* Точка имеет нулевую площадь: нельзя оценить зазор. Для робота 0,73×0,36 м проходимость определяется шириной прохода, а не расстоянием до центра.
- **H2. Показывать контур препятствия.** — *Принята.* Скан → кластеры по разрывам → выпуклая оболочка → линия контура.

**Решение.**
- подписка на `/robot1/scan`, фильтр по дальности (6 м), кластеризация по разрыву 0,25 м;
- выпуклая оболочка (монотонная цепь); стена схлопывается в отрезок и тоже показывается, если длина ≥ 0,15 м;
- статические препятствия фильтруются по карте: если точка попадает в занятую ячейку (с дилатацией 3×3), она не рисуется — стены уже на карте;
- публикация в `/im_obstacles`, дисплей добавлен в оба конфига.

**Итог.** 6–7 контуров в кадре, стены не дублируются. Коммит `f613df2`.

### П-9. Заливка контура не рендерится

**Проблема.** `Marker.TRIANGLE_LIST` для заливки полигона рендерился чёрным независимо от цвета.

**Гипотезы:**

- **H1. Неверный порядок обхода вершин.** — *Отвергнута.* Оба обхода (CW/CCW) дали тот же чёрный результат.
- **H2. Материал `TRIANGLE_LIST` в этой сборке RViz/Mesa игнорирует цвет маркера.** — *Принята как рабочая.* Заливка чёрная, контурный `LINE_STRIP` и `CUBE` рисуются корректно.

**Решение.** Для демо-препятствия (`source=demo`) используется `CUBE` + `LINE_STRIP`; для живых препятствий — только контур `LINE_STRIP`.

**Итог.** Форма читается, ложного чёрного пятна нет.

---

### П-10. TF лежит не в `/tf`

**Проблема.** Преобразование `base_link ← laser_frame` не находилось.

**Гипотезы:**

- **H1. TF вообще не публикуется.** — *Отвергнута.* `/robot1/tf` идёт с частотой ≈67 Гц.
- **H2. Топики TF в namespace робота, а издатель в глобальном.** — *Принята.* В `/robot1/tf_static` есть `base_link → laser_frame`.

**Решение.** Издатель запускается с ремапами `-r /tf:=/robot1/tf -r /tf_static:=/robot1/tf_static`.

**Итог.** Скан переводится в `base_link`, препятствия строятся. Коммит `24085cb`.

---

### П-11. `map` и `odom` расходятся

**Проблема.** ИМ рисует маркеры в кадре `map`, но трансформации `map → odom` нет. После движения робот оказался в точке `(-7,4; −4,0)`, то есть за пределами карты (`x ∈ [−5,06; 4,49]`), при этом коллектор отрапортовал `Navigation SUCCEEDED`.

**Гипотезы:**

- **H1. `map → odom` публикует SLAM.** — *Отвергнута.* `tf2_echo map odom` не находит кадр `map`; в `/robot1/tf` только `odom → base_link`.
- **H2. На старте `odom` совпадает с `map`, поэтому можно использовать `odom` как `map`.** — *Принята с оговоркой.* На спавне (0,0) это верно; после движения расхождение стало метрически значимым.
- **H3. Взять позу из `map → base_link`.** — *Отвергнута.* Кадра `map` нет.

**Решение (текущее).** Поза берётся из `/odom` и трактуется как `map`. Это записано как ограничение, а не как факт.

**Итог.** Для статичной демонстрации у спавна ИМ корректна; после длительного движения — нет. Нужен ремонт локализации: либо `slam_toolbox` должен публиковать `map → odom`, либо запуск с `SLAM=False` (AMCL по готовой карте).

### П-12. Кнопки не кликабельные

**Проблема.** `CONFIRM`/`CANCEL` — маркеры, а не виджеты.

**Гипотезы:**

- **H1. Можно повесить обработчик на маркер.** — *Отвергнута.* Маркеры RViz не принимают клики.
- **H2. Нужен custom RViz panel или внешний пульт.** — *Принята.*

**Решение.** Кнопки оставлены визуальными; в README и отчёте зафиксировано ограничение.

**Итог.** Не решено, вынесено в следующий шаг.

### П-14. `pkill -f` убивает собственный shell

**Проблема.** Команды очистки (`pkill -f "make gazebo"`, `pkill -f "ros2"`) завершали тот же shell, который их выполнял, и очистка не доходила до конца.

**Гипотезы:**

- **H1. `pkill -f` матчит командную строку самого вызывающего процесса.** — *Принята.* Строка `bash -c 'pkill -f "make gazebo"'` содержит искомый шаблон.

**Решение.** Убивать по `-x` (точное имя), по PID, либо использовать bracket-трюк (`pkill -f 'g[z] sim'` — шаблон не совпадает сам с собой). Для интерактивных целей — `script -qec 'make ...'`, чтобы дать TTY.

**Итог.** Очистка контейнера перестала рвать сама себя.

---

### П-15. `ffmpeg x11grab` и десятичная запятая

**Проблема.** Захват области `:0.0+0,982` парсился как позиция `0.982` и падал.

**Гипотезы:**

- **H1. Ошибка синтаксиса x11grab.** — *Отвергнута.* Синтаксис верный, но локаль использует запятую как разделитель дробной части.
- **H2. Нужно избегать запятой в аргументе.** — *Принята.* Захват полного экрана с последующей обрезкой в Python.

**Решение.** Для проверки мерцания используется захват по `window_id`; для областей — полный кадр и кроп.

**Итог.** Проверки работают.

---

### П-16. Правка коллектора не попадает в контейнер

**Проблема.** Исходники в контейнере лежат в volume `/root/ws/src`, а не в репозитории хоста.

**Гипотезы:**

- **H1. Правка на хосте применяется автоматически.** — *Отвергнута.* Volume не привязан к рабочему дереву.
- **H2. Нужен `docker cp` в volume и в установленный скрипт.** — *Принята для проверки.* Для чистой сборки нужен перезапуск сборки пакета.

**Решение (временное).** `docker cp` в `/root/ws/src/gazebo_sim/scripts/` (установленный файл — симлинк на него).

**Итог.** Работает в текущем контейнере; после пересборки образа правка применится штатно.

## 4. Как проверялось

### 4.1. Мерцание

`scripts/check_flicker.py`:

```
flicker: кадров=10 худший переход=0.38% плохих=0 порог=0.5%
```

Бисекция причины:

| Условие | Худший переход | Плохих кадров |
|---|---:|---:|
| Издатель остановлен | 0,00 % | 0 |
| Издатель работает, vsync включён | 93,19 % | 4 из 10 |
| Издатель работает, `vblank_mode=0` | 0,38 % | 0 |

### 4.2. FPS

Статусбар RViz на хосте (аппаратный GL, окно 3200×1800): **31 FPS**. В контейнере с software GL сцена обновлялась рывками; инструментальный замер не снимался.

### 4.3. Привязка к одометрии

```
/robot1/odom: x=0.013 -> x=0.733  (команда /robot1/cmd_vel, 0.2 м/с)
footprint в RViz: сдвиг на те же 0.73 м
waypoint 8: осталась на месте
```

### 4.4. Waypoints

| Шаг | `/waypoint_state` | Экран |
|---|---|---|
| старт | `count=0, active=false` | `WP: NONE`, точек нет |
| загрузка | `count=8, active=false` | `WP: 8 LOADED`, 8 серых |
| старт навигации | `count=8, active=true, current=0` | `WP: 1 -> 2`, 1 оранжевая, 2 синяя |

### 4.5. Навигация

Коллектор: `Navigation SUCCEEDED`, последний индекс 7 (восьмая точка). При этом одометрия в конце: `(-7,4; −4,0)` — за пределами карты. Это расхождение `odom` и `map` (П-11), а не ошибка ИМ.

### 4.6. Препятствия

`/im_obstacles`: 6–7 контуров (стены коридора, перегородки, мелкие объекты) в радиусе 6 м. Статические стены, совпадающие с картой, отфильтрованы.

## 6. Ограничения (осознанные)

1. **`map` в TF отсутствует.** `slam_toolbox` не публикует `map → odom`; ИМ трактует `odom` как `map`. После движения это неверно (П-11).
2. **Кнопки `CONFIRM`/`CANCEL` не кликабельные** — маркеры, а не виджеты.
3. **Путь — прямой отрезок** от робота до текущей цели, а не план nav2 (`/plan`).
4. **Препятствия — контуры лидара**, статика фильтруется по карте. Динамических объектов в мире нет; слой сенсорный, любой движущийся объект попадёт в него так же.
5. **Кириллица в маркерах не рендерится**; интерфейс ИМ на латинице.
6. **Коллектор в контейнере обновлён вручную** (`docker cp`); нужна пересборка пакета.
7. **`flicker-check` проверяет только старт** и только статичную сцену; при движении кадры законно различаются.
8. **FPS 31 измерен на хосте** (аппаратный GL); в контейнере с software GL цифра не снималась.
9. **Числа КР (PPI 290, 20′ и т. д.)** относятся к другому отчёту и здесь не пересчитывались.

---

## 7. Итог

Симуляция запускается одной командой с нужным RViz; ИМ берёт waypoints из коллектора, позу — из одометрии, препятствия — из лидара контурами. Мерцание устранено и проверяется автоматически; окно с мерцанием не выводится. Производительность восстановлена переносом RViz на хост с аппаратным GL.

Главный незакрытый дефект — отсутствие `map → odom`: до его устранения ИМ корректна у спавна и врёт после движения. Это ограничение локализации, а не визуализации.

## 9. Приложение. Команды и файлы

### 9.1. Запуск

```bash
# симуляция + ИМ + коллектор + RViz на хосте
make gazebo RVIZ=ergonomic

# без RViz
make gazebo RVIZ=false

# произвольный конфиг
make gazebo RVIZ=/path/to/view.rviz

# AMCL вместо SLAM
make gazebo RVIZ=ergonomic SLAM=False

# проверка мерцания
make flicker-check RVIZ=ergonomic

# уборка
make rviz-kill
```

### 9.2. Waypoints

```bash
make waypoint-load FILE=default.yaml
make waypoint-get
make waypoint-start
make waypoint-navigate INDEX=2
make waypoint-stop
```
