## Проблемы

1. **CPU fallback на AMD-ноутбуке без NVIDIA GPU** — 5 функций с Python-циклами (min_filter, max_filter, error_counting, base_elevation, sum_kernel) исполнялись как интерпретируемый Python, загрузка CPU до 100%
2. **GPU/CPU round-trips** — roughness и surface_gradient плагины копировали данные GPU→CPU→GPU на каждом кадре
3. **1240 строк мёртвого CUDA кода** — `kk.py` дублировал семантические ядра, добавляя путаницу
4. **Импорты в hot path** — `traversability_filter.py` импортировал numpy/scipy внутри каждой итерации

## Как были решены

1. **Numba @njit** — заменены 4 CPU-функции на скомпилированные версии (27-189× ускорение). Результаты bit-identical (< 1e-9).
2. **GPU path для roughness/surface_gradient** — добавлены прямые вызовы cupy без asnumpy/xp.asarray.
3. **kk.py удалён** — подтверждено отсутствие импортов через grep.
4. **Импорты наверх** — вынесены из `_apply_conv_bank` и `__call__` в глобальную область видимости.

## Что нужно учитывать в будущем

- **Numba компилирует @njit функции при первом вызове** — первый кадр после старта может быть на ~100ms медленнее. Проблема решается отдельным скриптом для pre-warmup.
- **Остались неоптимизированные семантические CPU kernels** (`custom_semantic_kernels.py:302-498`) — 8 функций с Python-циклами. Они не используются в стандартной LiDAR-конфигурации и не попали в hot path, но если понадобятся — Numba @njit даст аналогичное ускорение.
- **kk.py удалён безвозвратно** — если `kk.py` окажется нужным, его можно восстановить из git (`git checkout HEAD~1 -- kernels/kk.py`).
- **Общий прирост производительности CPU** — суммарное время 4 оптимизированных функций: c ~310ms до ~3ms за кадр (100×). GPU round-trip устранение: экономия ~0.5ms на плагин.
